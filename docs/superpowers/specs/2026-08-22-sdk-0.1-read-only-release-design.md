# OpenCoven SDK 0.1 Read-Only Release Design

**Status:** Proposed plan of record

**Date:** 2026-08-22

**Program:** [OpenCoven/sdk#31](https://github.com/OpenCoven/sdk/issues/31)

**Decision owner:** OpenCoven maintainers

## 1. Executive decision

The first public OpenCoven SDK release should be a secure, coherent **read-only protocol release**.

A separately installed client must be able to:

1. discover the owner-local Cave and Coven authorities;
2. verify protocol and minimum-client compatibility;
3. obtain a user-approved Cave credential;
4. place that credential directly into secure native custody;
5. validate the live Coven peer or named-pipe owner before trusting IPC;
6. read only the canonical familiars, projects, conversations, and messages it was granted;
7. survive process restart, endpoint relocation, and credential revocation without silently weakening trust;
8. prove the journey from packed artifacts against real authorities.

The first release deliberately stops before action. Message send, resumable streaming, attachments, task handoffs, and privileged GitHub mutations introduce materially larger authority and receive separate protocol, consent, idempotency, security, and conformance milestones.

## 2. Why this boundary

The repository is already strong in areas that normally lag behind a first implementation:

- five intentionally separated packages;
- import-time purity;
- caller-owned transports;
- stable normalized errors;
- operation deadlines, cancellation, and lifecycle observers;
- property, stress, package, and offline-consumer tests;
- checksummed release artifacts;
- protected-environment/OIDC release design;
- fail-closed publication locks.

The remaining asymmetry is that release machinery is ahead of the public developer journey. A green package verifier does not yet prove that a fresh consumer can discover, pair, retain a credential, validate native IPC identity, and read canonical state from real Cave and Coven processes.

The 0.1 boundary closes that gap without coupling first publication to the much larger mutation roadmap.

## 3. Release scope

### 3.1 Required for 0.1

#### `@opencoven/sdk-core`

- compatibility and capability contracts;
- operation controls and redacted lifecycle events;
- strict discovery record types;
- `SecretStore` abstractions;
- explicit page/cursor types and bounded iteration helpers;
- non-secret profile contracts;
- redacted diagnostics;
- public API baseline support.

#### `@opencoven/cave-client`

- source-locked Client v1 contract fixture and provenance;
- normalized compatibility health;
- secure owner-local discovery;
- pairing request, polling, exchange, status, and local forget;
- direct secure-store handoff for issued credentials;
- canonical familiars, projects, conversations, conversation, and message reads;
- explicit reconciliation and pagination behavior;
- no private Cave route fallback.

#### `@opencoven/coven-client`

- explicit discovery through reviewed `COVEN_HOME` and trusted fixed-argv CLI paths;
- Unix socket and Windows named-pipe validation;
- mandatory live peer/pipe identity providers;
- bounded health transport;
- structured daemon error preservation;
- no pathname-only, shell, PowerShell, `lsof`, private-internals, or permissive fallback.

#### `@opencoven/sdk`

- optional composition of separately configured/discovered Cave and Coven clients;
- total top-level deadlines;
- availability and health reporting without merging source-system identities or errors.

#### `@opencoven/dev-cli`

The CLI is included only if it implements the approved read-only operational surface with native secure storage and Coven trust adapters. Otherwise it remains private and the fixed release group is updated deliberately. Publishing a placeholder global binary whose operational commands return `not_implemented` is not an acceptable compromise.

### 3.2 Explicitly deferred

- conversation writes;
- message send, stop, retry, or stream;
- attachments;
- attention responses;
- task handoffs;
- GitHub mutations;
- arbitrary request or route escape hatches;
- speculative revision methods;
- offline mutation queues;
- cloud account or credential sync.

## 4. Trust model

### 4.1 Import-time purity

Package import performs no filesystem, process, network, socket, keychain, daemon, or discovery I/O. Every side effect begins through an explicit runtime call.

### 4.2 Cave discovery

The client reads only the reviewed owner-local discovery location. It validates the physical root, record type, ownership, mode, replacement state, size, record schema, live PID, bounded nonce, timestamp, and path-free loopback HTTP endpoint.

A configured timeout is one absolute monotonic budget covering filesystem inspection, parsing, and compatibility health. Cancellation may shorten the operation but never extend the budget.

### 4.3 Cave pairing and credential custody

Pairing is explicit user consent. The pairing secret is sent only through the reviewed header. The bodyless exchange sends `Content-Length: 0`. Proxy rejections are interpreted before Client v1 envelope parsing.

The one-time bearer passes directly into an injected `SecretStore`. After successful storage, the public operation returns credential metadata, not the bearer. No plaintext file, environment, browser storage, shell, log, observer, diagnostic, test artifact, or permissive fallback may retain it.

Local `forget` deletes local custody. It is not described as server revocation until a reviewed self-revocation route exists.

### 4.4 Coven IPC

A socket pathname or pipe name is not identity.

On Unix, the embedding runtime provides a reviewed adapter that inspects credentials on the exact connected socket. The SDK requires the peer UID to match the effective user and independently revalidates the pathname snapshot after connection.

On Windows, the embedding runtime provides a reviewed native adapter that validates pipe ownership before connection and connected pipe identity afterward.

The SDK never downgrades to pathname-only trust.

### 4.5 Diagnostics and error causes

Original causes remain available for local programmatic inspection but are sensitive by default. Public normalized metadata, lifecycle events, CLI output, and retained evidence are allowlisted separately and never copy arbitrary causes, stacks, command output, filesystem contents, pairing envelopes, credentials, prompts, message bodies, attachment data, or socket handles.

Redaction occurs before output format selection.

## 5. Contract governance

### 5.1 Producer provenance

Every vendored authority fixture records:

```ts
type ContractProvenance = {
  repository: string;
  commit: string;
  path: string;
  sha256: string;
};
```

The local digest verifier remains deterministic and offline. A separate parity gate proves that producer bytes at the named commit, vendored SDK bytes, packed-package bytes, and consumer-lock bytes are identical.

### 5.2 Operational capability truth

A capability means usable on the current authority. Planned route families do not appear indistinguishably beside live operations.

The selected Cave model may use broad capabilities, operation identifiers, or separate live/planned fields, but the SDK must be able to answer `supports()` without interpreting roadmap intent as runtime fact.

### 5.3 Compatibility health

The normalized Cave health result contains:

```ts
type CaveHealth = {
  status: "ok";
  apiVersion: string;
  minimumClientVersion: string;
  capabilities: readonly CaveCapability[];
  instanceId: string;
  releaseVersion: string;
  pairingRequired: boolean;
};
```

An unsupported API major or insufficient client version fails before pairing.

### 5.4 Public API governance

Every publishable package has a reviewed public API baseline derived from packed exports and declarations. CI fails on accidental export removal or incompatible signature change. Intentional breaking changes require a baseline update, migration note, and appropriate version change.

## 6. Canonical read model

The 0.1 client exposes only live Client v1 reads:

```ts
client.listFamiliars(options)
client.listProjects(options)
client.listConversations(options)
client.getConversation(id, options)
client.listConversationMessages(id, options)
```

No method calls Cave private routes. Search, commands, revisions, writes, and streams remain absent until the producer serves reviewed operations.

### 6.1 Pagination

One-page methods are primary. Iteration requires an explicit `maxPages`, caller-owned abort signal, or both. No helper silently downloads an unbounded collection.

The implementation preserves empty pages, exact and partial final pages, cursor replay, deleted-record continuation, non-canonical cursor refusal, page-size refusal, and `reconcile_required` when a message cursor no longer identifies the active branch.

The mutable conversation ordering limitation is documented honestly: moving an unserved conversation above an open descending cursor can skip it during that walk. A client needing a fresh snapshot restarts the canonical read.

### 6.2 Legacy Cave extensions

Existing Familiar Contract and execution-analytics operations do not silently masquerade as paired Client v1 reads. The release-scope decision must either:

- move them under an explicit extension namespace;
- publish them with separately documented authority/transport requirements; or
- defer them from the public 0.1 surface.

## 7. Real consumer and conformance

OpenCoven Chat is the first packed consumer. It installs exact tarballs, supplies native keychain and IPC identity adapters, and uses SDK APIs rather than duplicate protocol parsers.

A release-gating conformance journey proves:

- Cave discovery, health, pairing, restart, canonical reads, and revocation;
- Coven discovery, trusted executable handling, live peer/pipe identity, health, deadlines, and structured errors;
- packed artifact installation without source checkout;
- producer/vendor/pack/consumer contract parity;
- supported operating-system behavior;
- retained evidence redaction.

The evidence format declares every expected assertion ID and fails on missing, duplicate, unexpected, or silently omitted cases. Skips never count as passes.

## 8. Release model

Publication remains protected by two independent locks:

1. a reviewed repository change versions the approved package group and opens the repository publication lock;
2. a protected `npm-release` environment authorizes the deployment path.

The release sequence is:

```text
scope approval
→ governance prerequisites
→ security ship/block disposition
→ reviewed version/unlock PR
→ annotated tag
→ no-publish rehearsal
→ exact one-time bootstrap
→ bootstrap credential revocation
→ OIDC trusted-publisher configuration
→ registry/provenance validation
```

Normal future publishing uses OIDC only. `NPM_TOKEN` and `NODE_AUTH_TOKEN` fallback remain absent.

## 10. Deferred authority milestones

- [SDK #42](https://github.com/OpenCoven/sdk/issues/42): conversational creation, idempotent send, resumable stream, stop, retry, and reconciliation.
- [SDK #43](https://github.com/OpenCoven/sdk/issues/43): bounded attachments, rich semantics, task handoffs, and explicitly confirmed privileged actions.
- [SDK #44](https://github.com/OpenCoven/sdk/issues/44): encrypted replaceable offline reads, completions, scaffolds, and advanced tooling.

Each milestone receives its own authority-specific contract, security review, packed consumer proof, and real-authority conformance extension.

## 11. Decisions requiring maintainer approval

Before implementation leaves the reconciliation phase, record:

- approval of the read-only 0.1 boundary;
- whether the CLI ships or remains private;
- exact package group and versioning policy;
- exact Node range;
- release-supported OS/architecture matrix;
- treatment of legacy Cave extension APIs;
- native trust crate ownership and distribution strategy;
- safe diagnostic identifier/path policy;
- whether branch protection changes are required for release governance.

## 12. Completion definition

The program closes only when:

- all required implementation and consumer issues close with evidence;
- the exact packed candidate has a passing cross-repository conformance record;
- the security review recommends ship;
- the release is published through the approved protected path;
- registry bytes and provenance match the reviewed manifest;
- bootstrap credentials are revoked;
- future publishing uses protected OIDC only;
- root and package documentation describe the released surface and known limitations accurately.
