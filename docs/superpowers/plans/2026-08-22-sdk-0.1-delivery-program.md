## 1. Program objective

Deliver and validate a secure read-only OpenCoven SDK release in which a fresh packed consumer can discover Cave and Coven, negotiate compatibility, pair through user consent, retain credentials in native custody, validate live IPC identity, and read canonical state.

The program is organized as dependency-ordered gates. A later wave may prepare tests or design work in parallel, but it may not merge an API that assumes an unresolved upstream contract or weakens a trust boundary to bypass a blocker.

## 6. Wave 1 — implement the read-only protocol

### 6.1 PR sequence

Use small contract-focused PRs in this order:

1. `feat/cave-contract-provenance-health` — #33
2. `feat/cave-client-v1-discovery` — #34
3. `feat/cave-client-v1-pairing` — #35
4. `feat/cave-client-v1-canonical-reads` — #36
5. `feat/opencoven-cli-read-only` or `docs/defer-cli-from-0.1` — #37

Do not combine all five milestones into one feature branch. Each PR should preserve the previous public contract and add one independently reviewable authority boundary.

### 6.2 Required PR body structure

Every implementation PR must include:

- issue and dependency links;
- authority and trust-boundary summary;
- exact public API changes;
- explicit non-goals;
- compatibility statement;
- security-sensitive data-flow description;
- failing-test-first evidence where applicable;
- focused and canonical verification results;
- packed-consumer evidence;
- remaining blockers.

### 6.3 Close rules

A protocol issue does not close merely because mocks pass. Close requires:

- merged implementation;
- canonical repository verification;
- packed-package verification;
- required real-authority evidence named in the issue;
- documentation updated to the merged API;
- no unresolved review thread affecting correctness or trust.

### 6.4 SDK #36 branch surface

The implementation-complete branch exposes these one-page methods:
`listFamiliars`, `listProjects`, `listConversations`, `getConversation`, and
`listConversationMessages`. It adds bounded `iterateFamiliars`,
`iterateProjects`, `iterateConversations`, and
`iterateConversationMessages`; there is no iterator for the detail route.

The shared pagination contract defaults `limit` to exactly `50`, accepts only
safe integers through the maximum `100`, and rejects rather than clamps.
Cursors are opaque, strictly canonical base64url strings bounded to 512
characters; the SDK validates spelling without decoding producer semantics.
Every iterator requires a positive safe-integer `maxPages` or caller-owned
`AbortSignal` and lazily requests one page at a time, with no prefetch,
automatic retry, or implicit whole-corpus default.

Discovered reads use deterministic Client v1 `GET` routes. List queries always
insert `limit` before optional `cursor`; conversation IDs are encoded as one
path segment for detail and message routes. For legacy discovery v1, the
discovered bearer path first performs an unauthenticated instance proof and
then the authenticated request. That sequence is defense in depth rather than
atomic authority binding. Current `main` adds strict discovery v2 plus
`hpke-bound-v1` through PR #69 at `163961f4e59cfdef51d2271fa98e7c514977203f`,
paired with the producer/runtime implementation merged in
[`OpenCoven/coven-cave#5044`](https://github.com/OpenCoven/coven-cave/pull/5044)
at `2a0ff9237e94e652e477b22f60fd6d721b9e6451`, closing
`OpenCoven/coven-cave#4996`.

Success and explicit error envelopes require exact `apiVersion: "1.0"`,
`minimumClientVersion`, `capabilities`, and nonempty `operations`. Explicit
errors are preserved. Conversation `exitCode` is optional-nullable, message
`parentId` is required-nullable, and consumer-visible counts are strict
nonnegative safe integers. `reconcile_required` always instructs the caller to
reload canonical state and is never automatically retried, especially for
message drift reason `resume_from_canonical_state`.

Legacy `familiars()`, `familiarContract()`, and `familiarAnalytics()` remain a
separate compatible extension surface. Public-contract and packed-package
coverage resolves the new API and types from package-root imports and generated
tarballs.

### 6.5 SDK #37 release-scope decision

The 0.1 release tooling uses separate inventories:

- `WORKSPACE_PACKAGES` contains all five source packages and keeps the CLI
  covered by manifest, import-purity, command, keyring, and native-boundary
  tests;
- `PUBLIC_PACKAGES` contains the four release libraries and exclusively drives
  release configuration, Changesets fixed versions, packing, artifact
  manifests, publication, and registry validation.

No 0.1 release artifact installs or executes the `opencoven` binary. Chat #27
owns production native adapters and exact packed-library integration.

## 7. Wave 2 — first packed consumer

### 7.1 Chat integration

`OpenCoven/chat#27` owns:

- exact SDK tarball installation;
- Tauri/native Unix peer and Windows pipe identity adapters;
- native keychain-backed Cave credential custody;
- SDK-backed discovery, health, pairing, and canonical reads;
- Cave instance replacement and revocation handling;
- canary lock updates with commits and artifact digests;
- browser/webview secret exclusion.

### 7.2 Integration rules

- Chat may not copy SDK protocol parsers to get ahead of a blocked package.
- The webview may not receive bearer values.
- A pathname may not substitute for live peer identity.
- Workspace links are insufficient evidence.
- The canary must install the same artifacts intended for publication.

### 7.3 Exit gate

Wave 2 closes when Chat can complete the read-only journey from exact tarballs on every release-supported platform and produce evidence consumable by #38.

## 8. Wave 3 — cross-repository conformance

### 8.1 Required authorities

`OpenCoven/coven-cave#4996` is closed by
[`OpenCoven/coven-cave#5044`](https://github.com/OpenCoven/coven-cave/pull/5044)
at `2a0ff9237e94e652e477b22f60fd6d721b9e6451`, which lands the required Client
v1 atomic binding for pairing-secret and bearer-bearing requests. Final
security disposition still requires real-authority evidence on that merged
producer/runtime path. SDK health pre/postflight checks remain defense in
depth and must not be accepted as a substitute during conformance.

- release-mode Cave with isolated fixture state;
- real Coven daemon with isolated or controlled owner-local state;
- packed SDK tarballs;
- actual native keychain and IPC identity adapters;
- Chat or a purpose-built packed consumer.

### 8.2 Required evidence properties

- exact commits and artifact digests;
- stable complete assertion ID set;
- pass/fail/skip and diagnostic IDs;
- failure on missing/duplicate/unexpected assertions;
- negative-tested assertion helpers;
- representative broken-authority mutations;
- explicit `notCovered`;
- proof operator state was untouched;
- secret/content redaction scan.

### 8.3 Exit gate

SDK and Chat must no longer appear in `notCovered` for the 0.1 journey. A release candidate names one passing evidence record for every supported platform.

## 9. Wave 4 — developer governance

`#39` may proceed partly in parallel once public read DTOs and credential identity are stable.

Required deliverables:

- versioned non-secret profiles;
- explicit corrupt/reset behavior;
- allowlisted diagnostics with redaction before formatting;
- package public API baselines;
- packed export/type-resolution verification;
- compatibility, support, and deprecation docs.

Profiles must never become a second secret store. Diagnostics must never become an arbitrary cause serializer.

## 10. Wave 5 — security disposition

`#40` reviews the exact candidate after #38 and #39.
PR #69 alone does not authorize ship; this gate remains BLOCK until the exact
final candidate is re-reviewed with complete evidence.

Required evidence:

- `corepack pnpm@10.34.0 verify` on the reviewed commit;
- dependency audit;
- staged and full-history secret scans;
- packed API/export/type results;
- supported-platform native tests;
- cross-repository conformance record;
- release workflow negative tests;
- manual review of authority-bearing public methods and publishing path.

Every finding is fixed, explicitly accepted with follow-up, or blocks publication. The result is a written ship/block decision.

## 11. Wave 6 — external release execution

`#41` preserves the existing two-key release system and requires fresh authorization for each external mutation.
It remains locked and unauthorized while `release.config.json` keeps
`publishingEnabled: false` and the packages remain private.

Sequence:

1. approve exact version/package/platform scope;
2. verify npm ownership, 2FA, protected environment, and reviewers;
3. merge a reviewed Changesets/version/unlock PR;
4. create the annotated tag at reviewed HEAD;
5. run no-publish rehearsal and retain checksummed artifacts/attestations;
6. publish exact artifacts with one-time least-privilege bootstrap credentials;
7. revoke bootstrap credentials;
8. configure OIDC trusted publishing for every released package;
9. compare registry bytes, manifests, tags, provenance, and clean imports;
10. link evidence and close #31.

No issue, branch, or plan document grants publication authority by itself.
